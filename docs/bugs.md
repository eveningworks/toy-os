# Bugs

Defects that are **found but not fixed**: something here behaves
wrongly. Split out of `docs/roadmap.md` so that "what is broken" and
"what is not built yet" stop sharing a list -- they are different
questions, they are triaged differently, and a bug carries facts a
roadmap item does not.

**What belongs here:** something misbehaves -- a wrong result, a crash,
a flake, a control that does not respond. **What does not:** a
capability that does not exist yet, a design limitation, or a refactor
someone wants. Those stay in `docs/roadmap.md` under "Known limitations
and papercuts". The test is "is something broken?", not "would I like
this to be better?".

**A fixed bug is DELETED from here, not struck through.** That is the
opposite of the roadmap's rule and deliberate: a roadmap shows
progress, so a struck-through line earns its space, while a bug list is
only useful as a list of what is still wrong. `git log` is the record
of what was fixed -- point at the commit that fixed it if it needs
remembering.

**One line each; the repro lives in `docs/roadmap-details.md` under a
heading of the same name.** Same split the roadmap already uses, for
the same reason -- an index nobody can scan is an index nobody reads.

**Say the RATE for anything intermittent.** "5 boots in 9" is a
measurement; "sometimes" is a shrug, and the difference decides whether
a change made it better. And **say plainly when a cause was never
established** rather than implying one -- a plausible story that fits
the symptoms is not a diagnosis.

**PRE-EXISTING means MEASURED against an earlier commit,** not assumed.
`git stash push -u`, rebuild, and count before blaming your own change;
it has exonerated one this session and convicted another.

- [ ] **A USB3 HUB REBOOTS THE BARE-METAL ASUS, DETERMINISTICALLY, ABOUT 53 SECONDS IN -- almost certainly a TRIPLE FAULT.** Measured 2026-09-22, 2 boots in 2, reported by the maintainer as "it just rebooted itself" and confirmed in the logs. **Both boots end at the SAME LINE, 0.4 s apart**: `[52.46] usb: port 14: connected, super-speed, enabled (portsc 0x1203)` and `[52.84]` the same. A spontaneous reset on x86 with nothing logged is a triple fault. **WHERE IT IS**: the code that runs right after a SuperSpeed port reports connected, on port 14, immediately after port 13 has exhausted its retries and logged `enumeration GAVE UP`, `already replugged this episode` and `controller re-init already done or pending`. So the suspect path is enumeration of the SECOND SuperSpeed port while the first has already driven the retry/replug/re-init machinery. **WHAT LEADS UP TO IT**: every xHCI command to a SuperSpeed port times out at 1000 ms (`enable slot failed: vendor-defined`, `short device descriptor (-1)`), three retries per port, which is why the boot visibly crawls -- see the command-ring entry below, which this is probably a consequence of rather than a separate fault. **THIS WAS ONLY VISIBLE BECAUSE logd LEARNED TO fsync** (2ff4b3e8): the same two boots before that change came back 0 bytes with no header, and the evidence had to be photographed off the panel. **Recovery**: unplug the hub. The machine reboot-loops with it attached, and it has no usable USB meanwhile, so no network and no USB keyboard **STILL REBOOTS AT bd258bbf, so two candidates are EXONERATED by measurement.** (1) The freed-DMA-frame theory -- the strongest explanation for a triple fault rather than a panic -- is dead: `xhci_disable_slot()` now quarantines its frames when the command fails, the log confirms it fired (`disable slot 1: vendor-defined -- keeping its DMA frames`), and the machine reset anyway. (2) A kernel stack overflow was ruled out by measurement beforehand: the largest frame on the whole path is 344 bytes against a 16 KiB stack, and `#DF` is on IST1 so it would print rather than reset. **CONFIRMED FIXED on the way**, visible in the log: the `short device descriptor (-1)` lines are GONE, because `xhci_fail()` stopped turning the -1 timeout sentinel into a positive slot id. **The blind window is the obstacle now**: logd loses up to ~2 s on an unclean reset, and the log ends at 52.86 with the crash somewhere in [52.86, ~54.9] -- which covers port 14's first Enable Slot timeout and its first retry. Narrowing that needs either a shorter sync interval or breadcrumbs through the port-14 give-up path.

  **LINUX HAS THIS QUIRK, AND THE DEVICE CLASS MATCHES (2026-09-06).** `USB_QUIRK_DELAY_INIT` is "device needs a pause during initialization, after we get the device descriptor", and a follow-up patch puts `msleep(100)` BETWEEN THE FIRST AND SECOND GET CONFIGURATION REQUESTS -- added for the Logitech HD Pro C920 and C930e, which are WEBCAMS. `read_configuration()` here issues exactly those two requests back to back with no pause, and every device this OS repeatedly loses at `configuration N unreadable` is a webcam too: a Bison 5986:0670 on the Lenovo, a SuYin 064e:9700 on the ASUS -- the latter being the same device as the "internal port 5 never enumerates" entry, which nobody had connected to this one. Same request, same class, same symptom, from a kernel that has fought it for years.

  toy-os pauses on the RETRY rather than from a quirk table: the first attempt stays fast and a device that has already failed is asked again slowly, which gets the quirk's benefit with none of its cost on a healthy boot and no device-id list to maintain.

  **THE MEASUREMENT, AND WHY IT IS NOT YET A RESULT.** Ten boots per build on the Lenovo: 5/10 bad with the reset fix, 4/10 with command matching added, 2/10 with patience added. **At n=10 that last step is not significant** (4/10 to 2/10 is comfortably inside noise) and it should not be quoted as a fix. What IS suggestive is WHICH failures went: bad boots losing exactly ONE device numbered 3, 3 and then 0, while every remaining bad boot loses three or four ports together. That is consistent with TWO faults -- a slow device that only needed more time, which patience addresses, and a separate multi-port failure that it does not touch and that still shows the ports 4/5/6/8 shape. Thirty boots per build would settle whether the first is real.   **THE COMMAND-COMPLETION MATCHING BUG IS REAL AND IS FIXED, AND IT IS NOT ESTABLISHED AS THIS BUG'S CAUSE.** xhci_service()'s CMD_COMPLETION arm overwrote the waiter's expected TRB and set `done` unconditionally, so any command completion satisfied whatever command was waiting -- with that event's completion code and slot id. Since cmd_submit() leaves a timed-out command ON THE RING with no Command Abort, a late completion could hand the next port's command the wrong slot, which is a real way for one port to break another and matches the historical `address device (slot N) failed` signature. It is fixed (matched on its TRB, as Transfer Events already were, with unmatched ones counted and logged). **But the ten boots after the fix logged ZERO stale completions and ZERO command timeouts, so the mechanism never fired in them and cannot be credited with anything.** The rate went 5/10 to 4/10, which at n=10 is no change.

  This also explains what the earlier theories did not: why a replug always works (one enumeration, on an idle machine, with nothing before it to poison it), why the fault is correlated within a boot but not total, and why QEMU never shows it (no device ever stumbles there). **Next: make a failed enumeration prove it cleans up** -- log the slot, command-ring and endpoint state after one, and see what differs from a clean start.

  **MEASURE THIS ON THE LENOVO, NOT THE ASUS, and the reason is structural.** The ASUS's only network is the USB adapter, so when this bug fires there it takes away the very instrument used to observe it -- the machine is healthy and unreachable, and recovering it needs somebody physically present to reconnect the adapter (three times in one session on 2026-09-06, at roughly 2 boots in 4). The Lenovo has an ONBOARD PCIe NIC (r8169), so USB can fail completely and its log is still readable over the network. Both machines show the fault, so there is no reason to pay the ASUS's cost for it. **AND THE FIRST CORRELATION ANYONE HAS FOR IT, from the maintainer watching the machine: the firmware splash stays up LONGER on the boots where USB is lost.** That is a pre-OS difference, so whatever goes wrong is at least partly decided before toy-os runs -- which makes the BIOS-to-OS xHCI handoff the first thing to look at (`docs/conventions/kernel.md`, "THE BIOS OWNS THE xHCI UNTIL YOU ASK FOR IT"): a firmware that spent longer on its own USB phase may hand over a controller in a state the handoff does not expect. NOT established -- it is an eyeball correlation over a handful of boots, and the obvious next step is to time the handoff and log the ownership semaphore's state on every boot, so the correlation becomes a number that can be compared

Measured 2026-08-23 while adding Minesweeper. **`uterm` failed 3 of 5

The failing checks are all observation-timing ones -- a shell that did

the same class as the two entries above about injected clicks being lost

What would settle it: `tools/flake_hunt.py` over the full suite rather
than over a single tool, and a run pinned to fewer jobs (`-j 2`) to see

**2026-08-24: two of these had identifiable causes, and both were the
harness.** They do not close this entry -- the tool it lands on still
moves run to run -- but they narrow it, and the shape is worth knowing
before hunting the next one.

- **`font_test` slept 1.2s after each font change** instead of waiting
  for the compositor's own `wm: font changed` line. Three hops
  (a short-lived ring-3 process, the kernel, the client repaint) take a
  load-dependent total, so under load the ESTABLISHING change's line
  landed after the drain that followed it and the next `wait_log()`
  returned the PREVIOUS face's cell -- two different faces comparing
  equal. It failed 3 runs in 5 once an unrelated change made the desktop
  repaint more. Both setters wait on a line that is NEW since their own
  command now, and it passed 6 of 6 after.
- **`uapp_test` polled until the WINDOW existed** and the next check read
  its `resizable` HINT, which arrives over TWP afterwards -- a poll
  weaker than what follows it, which is this repo's own documented flake
  shape. It now polls for the hint.

**2026-08-29: a MECHANISM for this class now exists, and it is NOT
established that it was this one.** `serial_putc()` waited unbounded on
a THRE bit that QEMU's socket chardev stops setting when an attached
peer stops draining, so a guest whose console was attached but idle
stopped dead while its log had nowhere to go -- which is the shape of
every tool here (each holds a `DebugConsole` and then does QMP work).
That is fixed; output is queued now. **Three full-suite runs were clean
afterwards, which at these counts distinguishes nothing** -- 3 clean is
what a 40% rate produces about a fifth of the time. What would settle it
is `flake_hunt.py` over the full suite, which this entry already asked
for.

Neither was a new defect: both were fixed-sleep assumptions that a
busier machine invalidated. **When a tool in this class fails, read its
waits before suspecting the guest** -- and note that a suite run
alongside anything else (including a second `gui_regress`, which is
refused outright now) is competing for the same cores.

## `errno_test` and `focusring_test` fail intermittently -- FIXED 2026-09-14

**BOTH HALVES ARE FIXED, and each was a different fault.**
`focusring_test` was the HARNESS: a spawned test's verdict was collected
after a fixed 3-second sleep, so a slower boot reported a passing test
as truncated. It polls the verdict now, with a deadline that is a hang
guard rather than a budget.

`errno_test` was the KERNEL. There are two tables -- `FD_MAX`
descriptors per process and `FD_DESC_MAX` open-file DESCRIPTIONS for the
whole system -- and `open()` needs one of each, but `sys_open()`
answered EMFILE whichever ran out. A caller that exhausted the shared
table was told its OWN was full; the test believed it and required the
next `dup()` to fail, which it will not, since `dup()` takes only a
descriptor and shares the description it copies. `sys_open()` answers
ENFILE for the shared table now, as `sys_pipe()` already did, and the
test fills its table with `dup()` so nothing else on the machine can
reach it.

Kept as a record of the SHAPE rather than deleted: measured 2 of 3 boots
at commit 64f098e9, 2 of 4 with the storage work, 3 of 6 on 2026-09-14
-- always the same two tests, which is what said it was environmental
rather than a flake, and what eventually named both causes. Delete this
entry once it has stayed green for a while.
