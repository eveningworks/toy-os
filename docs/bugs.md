# Bugs

Defects that are **found but not fixed**: something here behaves
wrongly. Split out of `docs/roadmap.md` so that "what is broken" and
"what is not built yet" stop sharing a list -- they are different
questions, they are triaged differently, and a bug carries facts a
roadmap item does not.

**What belongs here:** something misbehaves -- a wrong result, a crash,
a flake, a control that does not respond. **What does not:** a
capability that does not exist yet, a design limitation, or a refactor
someone wants. Those stay in `docs/roadmap.md` under "Known limitations
and papercuts". The test is "is something broken?", not "would I like
this to be better?".

**A fixed bug is DELETED from here, not struck through.** That is the
opposite of the roadmap's rule and deliberate: a roadmap shows
progress, so a struck-through line earns its space, while a bug list is
only useful as a list of what is still wrong. `git log` is the record
of what was fixed -- point at the commit that fixed it if it needs
remembering.

**One line each; the repro lives in `docs/roadmap-details.md` under a
heading of the same name.** Same split the roadmap already uses, for
the same reason -- an index nobody can scan is an index nobody reads.

**Say the RATE for anything intermittent.** "5 boots in 9" is a
measurement; "sometimes" is a shrug, and the difference decides whether
a change made it better. And **say plainly when a cause was never
established** rather than implying one -- a plausible story that fits
the symptoms is not a diagnosis.

**PRE-EXISTING means MEASURED against an earlier commit,** not assumed.
`git stash push -u`, rebuild, and count before blaming your own change;
it has exonerated one this session and convicted another.

- [ ] **A PROCESS'S EXIT FREES ITS SIBLING THREADS OUTRIGHT, EVEN ONE THAT IS MID-CALL.** `group_release_threads()` calls `slot_release()` on every other thread of the group, whatever it is doing -- including one parked or woken MID-CALL, which may hold the filesystem lock across a disk wait. That would orphan the lock exactly as `scheduler_kill()` did before 2026-09-26 (see "Within a level, whoever has run least runs next" in `docs/decisions.md`), and every later file call would wait forever. **Found by reading the code, NEVER OBSERVED**: no test exits a process while one of its threads is inside a file call. Linux's `exit_group()` sends each thread SIGKILL and lets it leave at a safe point (`zap_other_threads()`), which is the shape a fix would take
- [ ] **ON THE PERIODIC TICK PATH, A LONE BUSY PROCESS GETS ABOUT HALF THE CPU.** The kernel context is a round-robin participant and its idle loop halts for the rest of its turn, until the next tick. One-shot mode hands over at once; the periodic path (`highres=off`, `option highres = no`, `nomsi`, `clocksource=pit`) has no way to cut the halt short. Measured 2026-09-24 with `tools/timer_bench.py` under TCG: 18663 work units at 100 Hz periodic against 33390 one-shot (and 17140 on the build before the one-shot work, which was always periodic). A self-IPI, or skipping the kernel's turn while it is idle, would fix it

- [ ] **A USB3 HUB RESETS THE BARE-METAL ASUS, AND EVERY SOFTWARE EXPLANATION IS NOW ELIMINATED.** The machine runs normally with the hub attached -- keyboard and mouse responsive, desktop usable, other devices enumerated -- and then resets, with nothing logged. **The time VARIES across boots (35, 45, 46, 47, 53, ~60 s) while the USB failure is IDENTICAL every time (always 17 command timeouts), so they are two phenomena, not one.** **WHAT THE HEARTBEAT ESTABLISHED** (`wedged_heartbeat()`, one line a second, only on a boot already broken): the machine is HEALTHY at the instant it dies -- the interval is a regular 1.01 s right up to the final line, with no slowdown, no spin and the timeout count frozen for thirty seconds beforehand. **AND THE HARDWARE REPORTS NOTHING**: the last heartbeat before a reset reads `usbsts 0x10 pcistatus 0x290` -- PCD alone, no `HSE`, and every PCI error bit clear (no master abort, no target abort, no SERR, no parity). **ELIMINATED, each by measurement rather than argument**: the device behind the hub (a BARE hub with nothing in it resets it just the same); over-current (the driver reads OCA/OCC now instead of clearing them unread, and neither ever fires); BIOS SMIs (the handoff is granted, `os-owned=1`, and the SMI disable runs whether or not it is); memory corruption (`meminfo --audit` reports no dangling mappings, taken from inside the failing state); freed DMA frames (quarantined since bd258bbf, and it still resets); kernel stack overflow (largest frame on the path is 344 bytes against 16 KiB, and `#DF` is on IST1 so it would print); and a software runaway (the heartbeat). **WHAT IS LEFT IS NOT REACHABLE FROM HERE**: no toy-os code is executing at the moment of the reset beyond a once-a-second print, and neither the controller nor the PCI bridge admits to an error. That does not make toy-os blameless -- something it does provokes the hub into whatever follows -- but the reset itself is not a fault this driver can see. **What would actually advance it**: boot Linux on the same laptop with the same hub and see whether it survives. If Linux resets too, the machine is at fault and this entry should say so; if it does not, the difference between the two drivers is the whole remaining question **AND THE HUB IS HEALTHY -- LINUX CONTROL, 2026-09-22.** The same Genesys Logic hub on the dev host enumerates FIRST TIME with no retries and no errors: `hub 3-1:1.0: USB hub found` / `4 ports detected` for the USB2 half at 480M, `hub 4-1:1.0` / `4 ports detected` for the SuperSpeed half at 5000M, and a Logitech receiver behind it at 12M bound to `usbhid` on all three interfaces. No `error -71`, no `device not accepting address`, no resets. **So the hardware is not at fault and neither is the device behind it** -- Linux reads `bNbrPorts = 4` from the very descriptor request that hands this driver 16 zero bytes. That makes `hub reports 0 ports` a REAL bug here, not a marginal device, and it makes port 2's intermittent `short device descriptor (-4)` ours too. **NOTE the static buffer experiment (ceca86c0) is STILL UNTESTED**: it only runs once `usb_hub_bind()` is reached, and the boots since have all failed earlier, at the device descriptor. It needs one of the intermittent boots where port 2 comes up.

- **`font_test` slept 1.2s after each font change** instead of waiting

a THRE bit that QEMU's socket chardev stops setting when an attached

## `errno_test` and `focusring_test` fail intermittently -- FIXED 2026-09-14

**BOTH HALVES ARE FIXED, and each was a different fault.**
`focusring_test` was the HARNESS: a spawned test's verdict was collected
after a fixed 3-second sleep, so a slower boot reported a passing test
as truncated. It polls the verdict now, with a deadline that is a hang
guard rather than a budget.

`errno_test` was the KERNEL. There are two tables -- `FD_MAX`
descriptors per process and `FD_DESC_MAX` open-file DESCRIPTIONS for the
whole system -- and `open()` needs one of each, but `sys_open()`
answered EMFILE whichever ran out. A caller that exhausted the shared
table was told its OWN was full; the test believed it and required the
next `dup()` to fail, which it will not, since `dup()` takes only a
descriptor and shares the description it copies. `sys_open()` answers
ENFILE for the shared table now, as `sys_pipe()` already did, and the
test fills its table with `dup()` so nothing else on the machine can
reach it.

Kept as a record of the SHAPE rather than deleted: measured 2 of 3 boots
at commit 64f098e9, 2 of 4 with the storage work, 3 of 6 on 2026-09-14
-- always the same two tests, which is what said it was environmental
rather than a flake, and what eventually named both causes. Delete this
entry once it has stayed green for a while.
